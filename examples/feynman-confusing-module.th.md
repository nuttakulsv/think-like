# ไฟน์แมน: อธิบายโค้ด retry ที่ไม่มีใครกล้าแตะ

> ตัวอย่างประกอบ ระบบและโค้ดเป็นเรื่องสมมติ

**คำสั่ง**

> คิดแบบไฟน์แมน อธิบาย `withRetry()` ในไฟล์ `http-client.ts` หน่อย ทุกคนในทีมใช้ แต่ไม่มีใครเข้าใจว่าทำไมบางทีมันรอนานเป็นนาที

**คำตอบ**

**สรุปในประโยคเดียว:** `withRetry()` ลองเรียก API ซ้ำเมื่อพลาด โดยรอนานขึ้นเป็นเท่าตัวทุกครั้ง แต่เพราะมันไปซ้อนอยู่ใน retry อีกชั้นของ axios เวลาที่รอจริงเลยคูณกันจนเป็นนาที

**ไล่ทีละขั้น** (ตัวอย่าง: เรียก `GET /stock` แล้ว server ตอบ 503 ตลอด)

1. `withRetry(fn, { retries: 5, baseMs: 500 })` เรียก `fn()` ครั้งแรก
2. `fn()` คือ `axiosClient.get('/stock')` แต่ `axiosClient` ตั้ง `axios-retry` ไว้ที่ 3 ครั้งอยู่แล้ว ดังนั้นการเรียก "หนึ่งครั้ง" ของ `withRetry` จริง ๆ คือยิง 4 ครั้ง (ครั้งแรก + retry 3)
3. พลาด → `withRetry` รอ 500 ms แล้วลองใหม่ จากนั้นรอ 1,000, 2,000, 4,000, 8,000 ms
4. รวมแล้วยิง request 6 × 4 = 24 ครั้ง และรอใน `withRetry` อย่างเดียว 15.5 วินาที บวกเวลารอของ `axios-retry` ข้างใน (ตั้ง timeout ไว้ 10 วินาทีต่อครั้ง) ทำให้กรณีแย่สุดเกิน 4 นาที

**ช่องว่างที่เจอ**

- ตอนแรกผมคิดว่า `retries: 5` แปลว่ายิงทั้งหมด 5 ครั้ง เปิดดูโค้ดแล้วไม่ใช่ มันคือ retry 5 ครั้งหลังครั้งแรก รวมเป็น 6 ครั้ง (แก้แล้ว)
- ไม่รู้ว่า `axios-retry` ถูกตั้งไว้ที่ไหน ค้นทั้ง repo เจอใน `src/lib/axios.ts` ซึ่งไม่มีใครพูดถึง (แก้แล้ว)
- ยังไม่รู้: request ไหนบ้างที่ไม่ควร retry เลย เช่น `POST /payments` ถ้า retry อาจตัดเงินซ้ำ ต้องถามทีม payment

**คำทำนายที่ลองได้:** ถ้าปิด `axios-retry` แล้วใช้ `withRetry` ชั้นเดียว เวลารอกรณีแย่สุดควรลดจากกว่า 4 นาทีเหลือราว 75 วินาที (รอรวม 15.5 วินาที + 6 ครั้ง × timeout 10 วินาที) ลองได้ด้วย mock server ที่ตอบ 503 ตลอด

**ข้อเสนอ:** เหลือ retry ชั้นเดียว, retry เฉพาะ GET และ request ที่มี idempotency key, ใส่ jitter และกำหนดเวลารวมสูงสุดต่อการเรียกหนึ่งครั้ง
